# 执行草稿续跑和表单定位（2026-10-12）

## 续跑必须保留案型

申请执行使用同一个 `zxfw-online-filing` skill 的 `--zhixing` 分支。用草稿 ID 时同时给 `--fyid`；完整执行 URL 会自动识别案型。`--goto` 与 `--resume` 均进入恢复流程，不能创建另一条草稿。

```bash
node filing.js <案件目录> --zhixing --resume <草稿ID> --fyid <法院代码>
node filing.js <案件目录> --zhixing --resume '<完整执行草稿URL>'
```

执行地址须使用 `ajlx=1501_000001-1002`、`ajcx=zx`。恢复后由 `step5Zhixing` 填写信息；不得调用民事一审的 `step5CaseInfo`。材料页先点“下一步”，等“申请执行人信息”出现。已在预览页的草稿只核对截图，最终提交仍由人工点。

## 表单逐项保存

- 输入框、下拉框、复选框和单选框均绑定字段所属的 `.uni-forms-item`，标签精确匹配优先。不得按三列表单中的屏幕位置猜控件。
- 下拉选项只匹配当前 `.uni-data-tree` 内的选项，排除已保存卡片上的同名文字。读取 `.selected-area` 的第一个节点确认值；弹层也可能使用同名类。
- 选择后触发遮罩的关闭事件，让组件自己收起弹层。仅设置 `pointer-events: none` 不能解决弹层遮住“保存”的问题。
- 申请人保存成功后再填写被执行人，随后保存代理人。任一必填项或保存失败立即停止并截图，不能继续操作仍打开的错误表单。
- 执行理由由平台在当事人信息保存后生成。执行请求照申请书；金钱给付金额按本金及已确定费用录入。不要点击“自动提取执行请求”。

## 同一登录配置不能并行运行

启动前检查 Chrome 的 `SingletonLock` 和脚本自身的 `filing-session.lock`。占用时说明进程仍存活，等待当前案件完成并关闭浏览器，不能认定为残留、终止另案进程或删除活跃锁。脚本不会自动关闭其他会话。

脚本正常结束会释放自身锁。异常退出后如果锁仍存在，先确认锁中 PID 已退出、Chrome 也不再使用该配置，再人工清理脚本锁。权限拒绝、程序崩溃与配置占用是不同原因，应根据报错判断。不能复制登录配置来实现并行。

操作中已采用按字段标签定位、精确选择和收起弹层、逐当事人保存的方法，成功进入执行案件的“预览和提交”页。正式脚本还须做语法、路由、字段歧义及锁占用的本地回归检查。不要为了检查代码再创建真实立案草稿；新组合或页面变化需在后续授权案件中继续核对。
